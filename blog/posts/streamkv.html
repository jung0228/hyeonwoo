Streaming VQA가 어려운 이유

오프라인 Video-LLM은 전체 비디오를 한 번에 처리한다. 실시간 스트리밍 환경에서는 이 패러다임이 근본적으로 맞지 않는다.

  • 끝없는 스트림: 비디오가 언제 끝날지 모른다. 전체 입력이 확정돼야 처리할 수 있는 오프라인 모델은 사용 불가.
  • On-the-fly 질문: 사용자 질문은 임의 timestamp에 도달한다. "지금까지 본 것"만으로 즉시 답해야 한다.
  • 메모리 선형 증가: 모든 프레임의 KV 캐시를 보존하면 비디오 길이 $T$에 비례해 GPU 메모리 증가 — 수천 프레임에서 OOM.
  • 실제 응용: 자율주행, Embodied AI, AR 기기 — 모두 실시간 응답이 전제.

선행 연구 ReKV의 세 가지 한계

ReKV는 KV 캐시 retrieval을 도입한 첫 시도다. 그러나 분할 방식·메모리·retrieval 정밀도에서 미해결 문제를 남긴다.

문제ReKVStreamKV (이 논문)
비디오 분할 Uniform partitioning — 씬 전환 중간에 경계가 생겨 semantic 구조 파괴 Cosine similarity 기반 동적 분할 — semantic boundary를 실제로 탐지
KV 저장 전체 KV 보존 — 메모리 $O(T)$, 수천 프레임에서 OOM Guidance prompt로 즉시 압축 → 고정 메모리, 90% 압축도 정확도 유지
Retrieval budget 레이어별 균등 할당 — 정보 분포 무시, 중요한 레이어에 과소 배분 Layer-adaptive allocation — similarity 분포 기반 binary search
학습 필요 여부 추가 모듈 학습 필요 Training-free — 기존 Video-LLM에 plug-and-play

StreamKV 전체 워크플로우

Segment → Encode → Compress → Bank → Retrieve → Answer. 각 단계는 동일한 Unified Layer-Adaptive Selection Module로 처리된다.

① Semantic Segmentation 인접 프레임 cosine similarity로 boundary 탐지 → 동적 분할. 각 세그먼트마다 summary vector $f_s^i$ 계산.
② Sliding-Window Encoding + KV Compression 세그먼트 단위로 순차 인코딩. Guidance prompt를 criterion으로 frame-level KV 블록을 즉시 압축 → KV Bank 저장.
③ KV Retrieval + QA 질문 수신 시 question vector를 criterion으로 KV Bank에서 관련 블록 검색 → answer 생성. Compression과 동일한 SelectKV 함수 재사용.
출처: Chen et al., StreamKV (AAAI 2026)05 / 13

Semantic Segment Partitioning

비디오를 균등하게 자르는 대신, 시각적으로 유사한 프레임끼리 하나의 세그먼트로 묶는다. 씬 전환 지점을 실제로 탐지한다.

경계 탐지 — Cosine Similarity 인접 프레임 임베딩의 similarity $s_t = \frac{f_{t-1} \cdot f_t}{\|f_{t-1}\|\,\|f_t\|}$ 를 매 프레임 계산. $s_t \le \theta$ (0.99)이면 씬 전환 → 새 세그먼트 시작.
길이 제약 Exclusion window $m=4$: boundary 직후 재분할 금지. 최대 길이 $M=64$: 초과 시 merging. 결과적으로 $T_i \in [m, M]$.
Summary Vector $f_s^i = \frac{1}{T_i}\sum_{t=1}^{T_i} f_t^i$ — 공간 위치별 프레임 평균, 세그먼트의 대표. 압축 제외, KV Bank에 항상 보존.
Representative Key (검색 인덱스) $\mathbf{r}_m^i = \frac{1}{P^2}\sum_{p} \mathbf{k}_{m,p}^i \in \mathbb{R}^{D'}$ — 각 KV 블록의 patch-wise key 평균. Compression/Retrieval 모두 이 벡터로 계산.
출처: Chen et al., StreamKV (AAAI 2026)06 / 13

Segment Merging & Sliding-Window Encoding

세그먼트가 $M=64$ 프레임을 초과하면 가장 유사한 인접 쌍을 병합해 길이를 줄인다. 비디오의 temporal redundancy를 활용한다.

Step 1 — Top-1 Similarity 선택 세그먼트 내 모든 인접 프레임 쌍의 similarity 중 최댓값인 쌍 $(f_j, f_{j+1})$을 병합 후보로 선택.
Step 2 — 평균 병합 $f_j' = \frac{1}{2}(f_j + f_{j+1})$ — 두 프레임을 하나의 merged feature로 교체. 세그먼트 길이 $T_i \to T_i - 1$.
Step 3 — Similarity 재계산 병합된 $f_j'$와 이웃 프레임 사이 similarity를 재계산. $T_i \le M$이 될 때까지 반복.
Sliding-Window Encoding $\mathbf{X}^i = [\mathbf{S}^i \| f_s^i]$를 local window $\mathbf{L}$ (15K tokens)과 함께 attention 계산. Context 길이를 고정 — 영상 길이와 무관.
출처: Chen et al., StreamKV (AAAI 2026)07 / 13

Unified Layer-Adaptive KV Selection

Compression과 Retrieval을 동일한 함수 SelectKV로 통합. 레이어마다 similarity 분포가 다르므로, budget을 균등 배분하지 않고 분포 형태에 따라 적응적으로 배분한다.

Step 1 — Cosine Similarity 레이어 $l$에서 criterion 벡터 $\mathbf{c}^l$과 candidate key $\mathbf{r}_j^l$ 사이 $\mathrm{Sim}_l(j)$ 계산. Compression 시: $\mathbf{c}^l$ = guidance prompt 벡터. Retrieval 시: $\mathbf{c}^l$ = 질문 벡터.
Step 2 — Softmax + 정렬 $$\widetilde{\mathrm{Sim}}_l(j) = \frac{\exp(\mathrm{Sim}_l(j))}{\sum_k \exp(\mathrm{Sim}_l(k))}$$내림차순 정렬 → priority sequence.
Step 3 — Binary Search for $p$ $$K_l^p = \min\!\left\{k \;\middle|\; \sum_{j=1}^k \widetilde{\mathrm{Sim}}_l(s_l(j)) \ge p\right\}$$총합 $\sum_l K_l^p = N$이 되는 global threshold $p$를 이진 탐색으로 결정.
Step 4 — Top-$K_l$ 선택 $$\{\mathcal{I}_l\}_{l=1}^L = \mathrm{SelectKV}(\{\mathcal{R}_l,\, \mathbf{c}^l\}_{l=1}^L,\, N)$$같은 함수를 Compression ($\mathbf{c}^l = \mathbf{g}^l$)과 Retrieval ($\mathbf{c}^l = \mathbf{q}^l$)에 모두 사용.

KV Compression via Guidance Prompt

스트리밍 환경에서 압축 시점에 사용자 질문은 알 수 없다. query-agnostic이면서도 semantically-rich한 압축이 필요하다.

왜 Question-based 압축이 안 되는가 SnapKV, FastV 등은 user question을 criterion으로 사용. 스트리밍에선 인코딩 즉시 압축해야 하는데 질문은 나중에 도달 — multi-turn까지 고려하면 특정 질문에 최적화 불가.
해결: Guidance Prompt Criterion 고정된 guidance prompt의 query 벡터 평균 $\mathbf{g}^l = \frac{1}{N_g}\sum_{k}\mathbf{g}_k^l$ 을 레이어 $l$의 criterion으로 사용.
압축 budget 압축률 $\theta$에 대해 $N = \lceil(1-\theta)T_i\rceil \times L$. Summary KV 블록 $\mathbf{b}_s^{i,l}$은 압축 제외, 항상 보존.
  • Salient entities: 사람, 사물, 장소, 핵심 시각 개념
  • Key events & actions: 무엇이, 언제, 어디서 일어났는가
  • Temporal & causal: 사건 전개 순서, 인과 관계 체인
  • Contextual cues: 씬 전환, 대화, 내러티브 변화
  • Numerical & factual: 카운팅, 요약, fact-based QA를 위한 수치

KV Retrieval & Question Answering

질문이 도착하면 동일한 SelectKV로 KV Bank에서 관련 블록을 검색한다. StreamKV는 8 frames만으로 정점에 달한다 — ReKV와 정반대 패턴.

Question Criterion Vector 질문 토큰의 query 벡터 평균 $\mathbf{q}^l = \frac{1}{N_q}\sum_{k}\mathbf{q}_k^l$. Retrieval budget $N = N_r \times L$ ($N_r = 8$ frames).
Retrieval $\{\mathcal{I}_l\} = \mathrm{SelectKV}(\{\mathcal{R}_l, \mathbf{q}^l\}, N)$ — Compression과 완전히 동일한 함수, criterion만 질문 벡터로 교체.
Positional Encoding (RoPE) 인코딩: local window 내에서만 RoPE (LM-Infinite). QA: retrieved token을 절대 위치가 아닌 상대 위치로 연속 취급.
핵심 관찰 Retrieved frames 늘리면 StreamKV는 정확도 하락 — precision이 높아 추가 프레임은 noise. ReKV는 반대.
출처: Chen et al., StreamKV (AAAI 2026)10 / 13

실험: StreamingBench 결과

18개 subtask, 3개 카테고리 (Real-Time · Omni-Source · Contextual). 동일 base model LLaVA-OV-7B 기준 비교.

Overall Accuracy ReKV 53.5 → StreamKV (↓60%) 58.9 (+5.4p). 90% 압축에서도 56.7 — 오프라인 베이스라인 56.4 상회.
Clips Summarization (CS) subtask 87.7% (60% 압축) — ReKV 대비 +9.1p, 베이스라인 대비 +11.7p. GPT-4o(83.9%), Gemini 1.5 Pro(83.5%) 모두 초과. Summary vector의 세그먼트 정보 보존 덕분.
Memory & Latency (10,000 frames 기준) GPU 메모리: LLaVA OOM → ReKV ~30 GB → StreamKV ~21 GB. Time to First Token: ReKV 0.8 s → StreamKV 0.55 s.
Omni-Source Understanding 4개 subtask 전부 proprietary MLLM 2개 초과. Layer-adaptive retrieval이 fine-grained visual detail을 정밀 검색한 결과.
